Memory infrastructure for agents

Agent memory you declare, not build.

Your app writes records. Memseek scores them, derives what they mean, and serves the few facts that are true now, each dated and cited to the event it came from. Nothing is ever overwritten.

What you store. Two shapes — an append-only log of things that happened, and a profile that keeps exactly one current value per field. Each is a versioned, schema-validated contract: a write that doesn't match is refused.

collections:
  - name: crm_events
    version: 1                # a change ships v2; v1 keeps serving
    mode: event              # immutable, append-only
    schema:                  # enforced at ingest, not at read
      required: [text, source, event_kind]
      properties:
        source:     {enum: [salesforce, hubspot, support]}
        event_kind: {enum: [role, commitment, preference]}
      additionalProperties: false   # no stray keys, ever
    fields:                  # lifted out of content, to filter on
      account_id: {path: content.account_id, filter: true}
    required_processors: [crm_embedding, importance]
    optional_processors: [deal_signals]   # may fail, won't block
    search_profile: pg_default        # how it ranks, by name
    # … plus the property enums, filterable fields, and ranking

  - name: user_profiles
    version: 1
    mode: keyed              # one current version per key;
                            #   rewrites supersede, never erase
    schema: {required: [text], properties: {tombstone: {type: boolean}}}
    required_processors: [crm_embedding]

How events become facts. Once enough important events pile up, one job — with a hard ceiling on calls, tokens and seconds — rewrites the profile. Citations are a required field of its output schema, so it cannot skip them.

name: crm_profile
trigger: {accumulator: {metric: importance, threshold: 6}, cooldown_s: 60}
sources:                   # all the run may see — every one capped
  new_crm_events:  {kind: changes, collections: [crm_events],
                    max_records: 100, max_tokens: 12000}
  current_profile: {kind: current, keys: [role, commitments],
                    max_tokens: 6000}
  commitment_history: {kind: view, view: crm_history, max_tokens: 3000}
model: strong              # an alias you repoint, not a model id
limits: {max_llm_calls: 2, max_total_tokens: 20000, max_wall_s: 60}
tasks:
  - id: result
    use: llm
    with:
      prompt: …             # the slot definitions, in the file
      output_schema:
        required: [key, text, citations]
        properties:
          key:  {enum: [role, commitments, preferences, goals]}
          text: {minLength: 1}
          citations: {minItems: 1, items: {format: uuid}}
# … and the task: one prompt, plus the output schema that makes
#   citations a required field — so no citation means no write
emit: {from: "{{result.records}}", collection: user_profiles,
       type: profile, keys: [role, commitments, preferences, goals]}

What your prompt gets. A declared call signature, then a fixed template with a token budget per block. Drop the result straight into your prompt; the same inputs always render the same bytes.

artifacts:
  - name: crm_profile_brief
    version: 1
    active: true               # publishable without being exposed
    kind: prompt
    lifecycle: live            # rendered on demand, always current
    parameters:              # the call signature, checked per render
      entity: {type: string, required: true}
      query:  {type: string, required: true}
    blocks:                  # in order, each with its own ceiling
      profile:  {document: {entity: "{{entity}}",
                              collections: [user_profiles], status: active},
                 max_tokens: 2000}    # trimmed to fit, never overrun
      evidence: {view: crm_history@1,
                 args: {entity: "{{entity}}", query: "{{query}}"},
                 max_tokens: 3000}   # a pinned view, budgeted
    template: |
      CRM PROFILE
      {{profile}}

      SUPPORTING CRM EVENTS
      {{evidence}}
      …
# plus a manifest per render: input_record_ids, tokens, rendered_sha256

run it locally

Four commands, then it's your data.

An API, a worker, and ordinary Postgres — so it runs wherever you decide to put it, starting with your laptop. You publish YAML, append events, and read what is true. There is no pipeline to orchestrate, no cron to schedule, and no queue to own.

01 · RUN

Two processes and a Postgres.

make quickstart starts PostgreSQL 16 + pgvector, applies the schema, and prints a workspace key. With LLM_FAKE=1 there is no API key to find — a deterministic stub provider stands in, so you can watch ingest, scoring, triggering, deriving and reading all work before you spend a token. The same two processes are what you deploy later, unchanged.

your terminal
$ make quickstart                    # postgres · schema · workspace key
$ source .env.sh && export LLM_FAKE=1 MEMSEEK_API_KEY=<key>

$ uv run uvicorn memseek.api:app     # terminal A · reads and writes
$ uv run memseek worker              # terminal B · embeds, scores, derives

# prefer to see it prove itself first?
$ make e2e                           # ingest → enrich → search → cited derive
02 · DECLARE

A memory product is a directory.

Collections, processors, derivations, views, artifacts and a package manifest — versioned YAML you review in a pull request, not code you maintain. This is the whole CRM example, and it ships in the repo.

examples/crm_profile_catalog/
crm_profile_catalog/
├── collections/crm.yaml            # crm_events (event) · user_profiles (keyed)
├── conf/processors.yaml            # embedding · importance score · deal signals
├── derivations/crm_profile.yaml    # accumulator trigger → cited keyed profile
├── views/crm_history.yaml          # hybrid search over the events
├── artifacts/profile_brief.yaml    # deterministic prompt block
└── packages/crm_user_profile.yaml  # the versioned bundle you publish
03 · WRITE

Publish it, then just append events.

Ingest returns immediately. In the background the worker embeds each event, scores how much it matters, and rewrites the profile once enough important events have piled up. Your application never orchestrates a pipeline.

app.py
from memseek.sdk import MemseekClient

async with MemseekClient(BASE_URL, API_KEY) as memseek:
    await memseek.catalog.publish(
        package="crm_user_profile@2.0.0",
        directory="examples/crm_profile_catalog",
    )

    await memseek.records.ingest_many([{
        "collection": "crm_events",
        "entity":     "contact:avery-chen",
        "type":       "crm_event",
        "text":       "Avery now owns the Atlas migration and "
                      "committed to an August launch.",
        "content":    {"source": "salesforce",
                       "event_kind": "commitment",
                       "account_id": "acme-cloud"},
        "dedupe_key": "sf:evt:88421",   # replay-safe
    }])
04 · READ

Four shapes, one layer.

Whatever your agent needs: the current cited beliefs, a bounded cited answer, a ready-made prompt block, or a small MCP tool surface. Same catalog, no second pipeline.

what you can build

Eight primitives. Every memory design you've read about.

Episodic and semantic memory, reflection, consolidation as in Anthropic's Dreams, a self-wiring graph as in Garry Tan's gbrain. Normally each is its own store and pipeline. Here each is those same eight, arranged differently: YAML you review in a pull request.

collectionsWhere records live: an append-only log, or one current value per field.
processorsSmall jobs that run the moment a record lands: embed, score, extract.
derivationsBudgeted jobs that turn events into stated facts, each one cited or dropped.
triggersWhat starts a derivation: enough events, a count, or a clock. You run no cron.
viewsSaved queries (search, graph walks, orphan checks) behind one name.
artifactsPrompt assembly under a token budget, with a receipt of what went in.
packagesThe versioned bundle you publish to a workspace.
mcpThe short list of tools an agent may see, and nothing beyond it.
walkthroughs · one per memory kind people already nameno privileged internals
semantic · graph An entire brain, declared Five markdown pages land; the graph and the fact index extract themselves at zero model calls. why it isn't RAG

Retrieval finds what looks similar.
Memory knows what's true now.

Reliable memory is context selection, not context volume — the part a vector search was never built to do.

plain RAG vector search

  • ✕
    Returns chunks that look similar — no idea which one is current.
  • ✕
    Contradictions arrive side by side and the model guesses.
  • ✕
    Dumps the whole history into the prompt to be safe.
  • ✕
    Sources and dates fall off along the way.

memseek declared memory

  • ✓
    Serves the few facts that hold now, with what they superseded still on record.
  • ✓
    Reconciles sources into one coherent picture, and flags real contradictions as events.
  • ✓
    Compact context — ~32× fewer tokens than the full history.
  • ✓
    Every belief cites its evidence or is rejected. Point-in-time replay included.

The long version, and the failure it comes from: Your agent doesn't need more context. It needs the current context.

buy vs. build

The same reason you don't hand-roll your own Postgres.

A real memory layer is substantial engineering most teams don't solve well. The question isn't whether you could build it. It's whether that's the best use of your team.

straight answers

The questions we actually get asked.

Isn't this just RAG?+
No. RAG retrieves text that looks similar. Memseek maintains current, keyed beliefs derived from immutable events: it knows what superseded what, flags contradictions as first-class records, requires a citation for every derived belief, and serves ~32× fewer tokens. On public benchmarks it beats standard dense retrieval by +7.5 to +10.8 points on multi-hop QA. Hybrid retrieval is one primitive inside it, not the product.
How long until I see it working?+
Four commands. make quickstart brings up PostgreSQL 16 + pgvector, applies the schema and prints a workspace key; then you start the API and the worker. Set LLM_FAKE=1 and you need no provider account at all — a deterministic stub stands in for the model, so the whole loop runs and you can read the audited run it produced. make e2e does that end to end as an acceptance test. Point it at a real model when you want real language out of it.
Where does my data live?+
Wherever you choose to put it — it's an API, a worker, and PostgreSQL 16 + pgvector, so it deploys like anything else you already run. Run it in your own VPC today and nothing leaves your infrastructure except the model calls you configure, which can point at a model you host yourself. The property that holds either way is portability: records are ordinary rows you can query and export, and writes are append-only — a rewrite supersedes, it never overwrites — so point-in-time reconstruction and recursive-closure erase stay possible no matter who operates the database.
What do I actually get back?+
Four shapes from the same catalog: a document of current cited beliefs, a bounded cited answer with declared gaps, a deterministic prompt artifact with a hashed input manifest, or a small MCP tool surface. Plus ordinary hybrid search when you want the raw records.
How much control do I have over cost and behavior?+
Every derivation declares hard limits — max_llm_calls, max_retrieved_records, max_total_tokens, max_wall_s — and models are referenced by alias, so swapping providers is a config change, not a redesign. Several adapters run with max_llm_calls: 0: structural extraction with no model in the loop.
Will it change things without asking?+
Only what you declared. Write-triggered derivations maintain the slots they own; anything gated (a revised skill, a rebuilt profile) lands as a reviewed draft that stays in the audit trail until you promote it. Feedback becomes ordinary records, never an automatic change.
Does it need an expensive frontier model?+
No. The benchmark results above are on inexpensive, self-hostable models. Model aliases let you put a strong model on the one derivation that needs it and a cheap one everywhere else.
What does it cost to run?+
A PostgreSQL instance — the kind you are probably already paying for — plus the model calls you declare, and you declare their ceiling per derivation: max_llm_calls, max_total_tokens, max_wall_s. Reading is the cheap part: roughly 3,200 tokens of assembled context per question instead of ~101,000 for the raw history, on every call your agent makes for the life of the product. Several adapters run at max_llm_calls: 0 and cost nothing but Postgres.
How is this different from the memory products I've already seen?+
Most sit in one of two camps: a service that keeps your snippets and hands back whatever looks relevant, or memory built into a model vendor's product, where the store, the rules and the model are all theirs. Memseek is infrastructure, and the parts that matter stay yours: the rules are YAML in your repo and reviewed like any other change, the records are ordinary Postgres rows, the model is an alias you can repoint at any provider, every derived fact has to cite the events it came from, and nothing is promoted unless you declared that it could be. We put one of those comparisons on the page side by side — see the dreams showcase.
